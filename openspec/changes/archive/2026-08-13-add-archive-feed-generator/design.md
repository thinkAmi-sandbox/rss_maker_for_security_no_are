# Design: セキュリティのアレ 過去回アーカイブフィード生成ツール

## Context

公式フィードは最新300件のみを配信し、過去回はサーバーから取得不能(ページング・RFC 5005 不使用、Spotify/Apple は同一フィードのミラー)。音源ファイル自体は公式サーバーに現存する。本設計は 2026-08-13 の調査・設計セッション(PLAN.md)と、その成果物への敵対的検証(3エージェントによる一次情報検証)、および検証指摘の逐次検討の結論を統合したものである。**本ドキュメント群が唯一の正であり、PLAN.md は吸収済みのため廃棄する。**

想定ユースケースは「番組を新しく聴き始める人が、その時点の取りこぼしを1回だけ自分のプレイヤーに取り込む」こと。**永続公開されるフィードを運営するツールではない**。この前提が件数ガードの設計(後述)を大きく左右している。

### 検証済みの事実(2026-08-13 実測)

- 公式フィード: ちょうど300 item、最古は第15回(p=491)。`?paged=2` は 404 ではなく**同一内容の 200** を返す
- **guid はスキーム混在**: https 227 / http 73。`isPermaLink="false"` と `www.tsujileaks.com/?p=NNN` 部分は300件全件で不変。分布は「p≦846 は全件 http → p=847〜1587 は https 優勢に http が7件点在 → p≧1588 は全件 https」。混在は時期から決定論的に予測できない
- `<link>` 要素は300件全件 https(WordPress が配信時に正規化)。guid とは別物であり、`<link>` と guid の p 番号は全件一致
- ファンリポジトリの自動更新 CSV: 387行(S1=26, S2=45, S3=316)。GitHub Actions(`daily_update.yml`)が **12時間ごと**に `?feed=rss2` を読んで追記する**蓄積型**(既存行を削除するコードパスなし、履歴上も削除ゼロを確認)。S1+S3 の342行は全行 `https://www.tsujileaks.com/?p=NNN` 形式で p 重複なし。S2 は全行 atmarkit URL・audio_url 空
- CSV の `recorded_date` は 1900-01-01 ダミー189行/実日付198行の**信頼できない混在**(由来判定にも使えない)
- `num` は S3 内で重複あり(6, 7, 24)。一意なのは p 番号と `id` 列のみ
- 出力対象42回(S1 全26回 + S3 第1〜14回+雑談2本、p=10〜488)の音源は**全件 https で生存**(HEAD 実測、Content-Length / Content-Type 取得可)。音源サーバーは `accept-ranges: none`
- ファンリポジトリは MIT(LICENSE 確認済み)。日付付き JSON(`scraping_2025-06-07.json`)は一回きりの生成物で S2 を含まず、メンテされていない
- podcast_player(注入先アプリ)はエピソードを `(feedId, guid)` の**ユニークインデックス+文字列等価**で識別(`insertIgnoringKnown` は既知 guid を挿入無視)。enclosure 非空が取り込みの必須条件。取得を許可するのは https のみ(`HttpUrlPolicy`)だが、取り込み時にスキーム検査はない(http enclosure は「一覧に出るが再生できない」状態になる)

## Goals / Non-Goals

**Goals:**

- ファン CSV と現行フィードの差分から、標準 RSS 2.0 のアーカイブフィードを冪等に生成する
- guid の正しさを最優先で守る(台帳+合成+fail-loud 監視)。アプリ側の重複排除はこれに全面依存するため
- 静かな故障(形式ドリフトによる全量出力、正当な回の無言の欠落)を fail-loud で検出する
- 公式サーバーへの礼儀(順次 HEAD・間隔・明示 UA・最小リクエスト)

**Non-Goals:**

- 汎用ツール化(任意の番組対応・Wayback 抽出)。知見は README のレシピとして文書で残す
- 全量配信(公式配信中の回は出力しない)・音源の再ホスト・永続公開・自動更新/定期実行
- S2(@IT 動画時代)の収録。**ポリシー決定**: 本ツールは音声ポッドキャストのアーカイブであり、@IT がホストする動画連載は別メディアとして対象外(全45記事の音源不存在を検証した事実主張ではない。確認したのは1記事のみで、そこは @IT 公式 YouTube への埋め込みだった)
- duration の補完(YAGNI。アプリ側で duration 欠落が通常状態であることを確認済み)

## Decisions

### D1. データソース: 自動更新 CSV(JSON ではなく)、既定はリモート直接取得

`source/_static/セキュリティのアレ_放送回リスト_自動更新.csv` を入力とする。**代替案**: 当初計画の `scraping_*.json` は一回きりのスナップショット(2025-06-07、作者が「メンテしていない」と明言)であり、蓄積が止まっている。CSV は12時間ごとに自動追記される蓄積型で、押し出された回も残り続けるため、フィード保持件数への依存が消える。ファイル名固定なので「複数ファイルからの選択」問題も存在しない。列はヘッダ名でアクセスし、必須列の存在をアサートする。

**取得方法**: 利用者は Python さえあれば動くことを優先し、既定ではツールが GitHub から直接取得する。「GitHub API で main の sha を確定 → その sha に固定した raw URL からダウンロード」の2段構えにすることで、2リクエストの間に push が挟まっても記録する sha と取得内容が食い違わない。内容はメモリ上で処理し保存しない(sha があれば raw URL から同一内容を再取得できるため)。`--csv`(ローカルパス指定)は開発・オフライン再現・ファンリポジトリ消滅時のバックアップ用として残す。ローカル指定時のハッシュは、`git ls-files --error-unmatch` で「その CSV が見つかったリポジトリの追跡ファイルである」ことを確認できた場合のみ採用する(git の親方向 walk が無関係なリポジトリの HEAD を拾い、誤った出典を記録する事故の防止)。日本語ファイル名の NFC/NFD 懸念はファイルシステム探索の話であり、コード内の URL 定数(バイト列固定・URL エンコード済み)には該当しない。

### D2. 差分は p 番号ベース(guid 文字列比較ではなく)

公式 guid のスキーム混在(検証済み事実)により、guid 文字列比較は https 227件を「フィード外」と誤判定し、全量出力=公式ホスティングの複製へ**沈黙のまま**転落し得る。p 番号は CSV の `url` とフィードの guid の双方から機械的に抽出でき、342行+300件で重複ゼロを確認済み。フィード全 guid の形式アサーション(`^https?://www\.tsujileaks\.com/\?p=\d+$`)を通過させてから p 番号を抽出することで、形式ドリフト時は fail-loud になる。

### D3. guid 戦略: 観測台帳 + http 合成のフォールバック

アーカイブ item の guid は「台帳の観測値 → なければ `http://www.tsujileaks.com/?p=NNN` を合成」。台帳(`data/guid_ledger.csv`)は生成コマンドに内蔵して毎回追記更新し、リポジトリにコミットする。**根拠**: 台帳開始以降に押し出される回は観測済みの実 guid が使え、推定が不要になる。台帳開始以前に押し出された回(p=10〜488)は合成に頼るが、隣接帯44件(p=491〜846)が全件 http である実測と2017年スナップショットから http が最善の推定。**代替案として棄却**: ファンリポジトリからの guid 取得は不可能(CSV の `url` は `<link>` 由来であり guid は未保存)。既知 p での guid 食い違いは fail-loud とし、「公式が過去回を別 guid で再配信し始めたら本ツールは役目を終える」と割り切る。

### D4. 件数ガードは「サマリ表示+フィード0件中断」のみ(縮小決定)

当初は「出力が想定42件を大きく超えたら停止」する強いガードを検討したが、以下の理由で縮小した: (1) ユースケースが1回きりの取り込みであり、guid が正しければ大量出力でもアプリ側で重複しない(台帳導入の帰結)、(2) フィード保持件数は配信側の設定値で、過去に10→300へ変わった実績があり、窓縮小時に強いガードは**正しい動作を異常と誤判定**する。**フィード件数(300)や差分件数(42)を実装・テストの不変条件にしないこと**。機械判定は「フィード item 0件での中断」(空 XML の取得劣化は形式アサーションが素通りするため)のみとし、それ以外の件数は実行サマリとして表示して目視に委ねる。

### D5. 除外の不変条件: 「除外行はすべて season == 2」

処理対象の選別規則(`?p=NNN` 形式 url + 非空 audio_url)は現データで S1+S3 / S2 を完璧に分割するが、規則単体では「正当な新回が無言で欠落する」将来変化(URL 形式変更、audio_url 空化)を検出できない。除外集合が S2 と一致することを毎回検査し、S2 以外の除外・未知 season は fail-loud にする。判定キーはドメインではなく `season` 列を使う(除外のポリシー根拠「S2 は動画連載」と検査条件を一致させるため。将来 S4 が現れた場合も未知 season として検知される)。

### D6. enclosure は常に https 書き換え後の URL で統一

生存確認の結果に依存させない(冪等性)。https 死・http 生のケースでも https を入れる: (1) podcast_player は https のみ取得可(`HttpUrlPolicy`)で、http を入れると「一覧に出るが永遠に再生不可」になる、(2) サーバー側が直れば XML 再生成なしで再生可能になる(復活への賭け)。生存確認の結果はタイトル接頭辞【音源リンク切れ】と description(検出日時・元 URL・http では取得可能か)のみに反映する。バッジは2ケース(https死のみ/両方死)で共通とし、区別は description に書く。なお実測では出力対象42件の全音源が https で生存しており、導入時点でバッジ対象はゼロ件の見込み。enclosure の `length`/`type` には HEAD で得た実値を入れる(Wayback に見られた 5MiB 固定の偽値を作らない)。リンク切れで実値が取れない場合、`type` は拡張子からの推定値になる(RSS 2.0 で enclosure の `type` は必須属性のため省略できない。公式の実配信は同じ .m4a に `audio/mp4` と `audio/x-m4a` の揺れがあり、推定値は前者に寄せる)。任意属性の `length` は実値が無ければ省略する。

### D7. レンダリングは XML API で構築(文字列連結禁止)

タイトルに `&` を含む実データが存在する(S2#29)。Python 標準の `xml.etree.ElementTree` 等で要素として構築し、エスケープ漏れを構造的に防ぐ。

### D8. モジュール構成とテスト戦略

判断(純粋関数)と I/O を分離する。モックライブラリは使わず手書き Fake。

| モジュール | 純粋? | 責務 |
|---|---|---|
| `load.py` | 純粋 | CSV の解釈・必須列検証・p 番号抽出・S2 除外と不変条件(D5) |
| `guid.py` | 純粋 | guid 決定順位(台帳参照→http 合成)(D3) |
| `diff.py` | 純粋 | フィード XML から guid 形式アサーション+p 番号集合抽出、差分決定(D2)、CSV 未収載 p の検出 |
| `ledger.py` | 純粋 | 台帳の読み込み・追記計算・食い違い検出(D3) |
| `render.py` | 純粋 | 差分 item + channel メタ → archive.xml 文字列(バッジ・description 含む)(D6, D7) |
| `fetch.py` | I/O | フィード GET・音源 HEAD(https→http フォールバック)。レート制御・UA |
| `cli.py` | 結線 | 引数解釈・パイプライン実行・実行サマリ表示・台帳ファイル書き出し |

テスト: 純粋モジュールは unittest 直+実データ断片のフィクスチャ。guid 合成と差分は入力空間が小さいので網羅的に。render は golden file。`fetch` は関数注入で Fake に差し替え。**テストの期待値に「フィード=300件」「差分=42件」のようなライブデータ依存の不変条件を書かない**(フィクスチャ内の固定データへの期待値は可)。エピソードの同一性は p 番号のみで扱い、`num`(S3 内で重複あり)や `title` をキーにしない。

### D9. 実行サマリ

目視確認(運用フローの必須ステップ)の材料として、フィード件数・処理対象・除外内訳・出力内訳・リンク切れ件数・台帳追記件数を表示する。加えて「フィードに在るが CSV に無い p 番号」を警告表示する(ファンリポジトリの Action 停止の兆候を利用者が察知できる唯一の窓)。

## Risks / Trade-offs

- **[公式が過去回を再配信し、guid が合成値と異なる]** → アプリ側で重複が発生し得る。ただしその状態は「公式で過去回が聴ける」ことを意味し、本ツールの役目が終わる。台帳の食い違い検出が兆候を検知する
- **[ファンリポジトリの Action 長期停止 → 再開時の無警告ギャップ / リポジトリ消滅]** → CSV の鮮度は外部依存。停止の兆候は D9 の警告で検知。`references/` のローカル clone がバックアップを兼ねる(MIT なので合法)ことを README に明記
- **[S2 の44記事は音源不存在を実地確認していない]** → 除外をポリシー決定として記述することで、事実の未確認が仕様の弱点にならない構造にした(D5, Non-Goals)
- **[合成 guid は推定であり保証がない]** → 「歴史的証拠に基づく最善の推定」と README に明記し、過剰な保証を謳わない
- **[音源サーバーは accept-ranges: none]** → プレイヤーのシーク・レジュームが効かない可能性。こちらで制御不能な既知事項として README に記載
